# CLI 루프 사용법 (agy ReAct 에이전트용)

> 이 문서는 **CLI 에서 도는 에이전트**가 읽는다. 위 SKILL 본문의 절차(01 → 생성기 → 02 → 03 → 한 가지씩 고치기)는 같다.
> 다른 점은 **너는 파일을 고치거나 01 · 02 · 03 을 직접 실행하지 않는다**는 것이다. 호스트가 만든 도구(팔)가 대신한다.
> SKILL 본문의 `python ...` 명령어 · "생성기 작성"은 IDE 작업자용이다. CLI 에서는 아래 도구를 쓴다.

## 1. 누가 무엇을 하나

| 하는 일 | 누가 |
| :--- | :--- |
| 원본 PDF → `truth.json` (글자 좌표 · 글꼴 · 자간 토큰 · 선 · 그림) | 호스트가 시작할 때 한 번 (01, 글꼴 파일과 함께) |
| 줄 묶기 · 표 격자(선 → 행 · 열 · 합친 칸) · 글자를 PDF 좌표에 놓기 · 자간 · 줄 높이 F | **생성기 (결정적)** — 같은 입력이면 같은 문서 |
| 표 밖 글 줄을 **어떤 블록으로 묶고 무엇이라 부를지** (분할안), 표 이름 | **너** — `set_plan` |
| 브라우저와 PDF 의 **체계적 차이**를 미는 보정값 | **너** — `update_tune`, 단 진단이 준 처방대로 |
| 디버그 크롬에 띄우기 → 02 재기 → 03 판정 → 원인 진단 · 처방 | 호스트 — `evaluate` 한 번에 |
| 완료 판정 · 보고 숫자 | 03 (호스트가 마지막 결과에서 채움) |

## 2. 도구 (팔)

| 도구 | 언제 | 인자 |
| :--- | :--- | :--- |
| `read_lines` | 분할안을 정하기 전, 또는 어느 줄이 어느 블록인지 볼 때 | `from` · `to` (줄 id), `where` (B3 · T1 · T1.r2c1) |
| `read_tables` | 표가 있을 때 칸 구조를 볼 때 | `table` (T1) |
| `set_plan` | 기본 분할안이 조항 · 문단 단위가 아닐 때 **한 번에** | `blocks`, `table_titles`, `reason` |
| `evaluate` | 무엇이든 바꾼 뒤 **반드시** | 없음 |
| `update_tune` | 처방(`prescriptions[].action`)이 있을 때 | `changes` = 처방의 `action.args.changes` 그대로, `reason` = 처방 id |
| `inspect_spans` | 처방이 없는데 `individual` 이 남았을 때 그 블록 · 줄을 자세히 | `block` 또는 `line` |
| `revert` | 점수가 떨어졌을 때 | `iter` (생략하면 최고 점수 반복) |
| `get_state` | 지금 보정값 · 분할안 · 이력을 다시 볼 때 | 없음 |
| `finish` | 목표 도달, 또는 처방이 더 없고 `engine_issues` 만 남았을 때 | `summary` |

## 3. 순서

1. **과제의 쪽 개요를 읽는다.** 표 밖 글 줄이 있으면 기본 분할안이 맞는지 본다.
   - 좋은 블록: 문서 제목 · 조항(`제N조` 머리 + 딸린 항목 `1.` `2.` …) · 부칙 · 서명란 · 날짜처럼 **사람이 한 덩어리로 고치는 단위**.
   - 번호 항목 하나하나를 블록으로 쪼개지 않는다. 쪽 머리 · 쪽 번호처럼 떨어진 것은 따로.
   - 블록 이름(`title`)은 한국어 업무 용어로 짧게 (예: `제2조 기능`, `부칙 시행일`). 표 이름도 (`회의 개요표`).
   - 기본안의 이름은 첫 줄 글자를 자른 것이라 그대로 두지 않는다. 경계가 맞아도 `set_plan` 한 번으로 이름을 전부 정한다. 표만 있는 쪽이면 `table_titles` 만.
   - **`set_plan` 을 한 번도 부르지 않으면 `finish` 가 거부된다.** 첫 턴에 하는 것이 가장 싸다.
2. `evaluate`.
3. 관찰의 `prescriptions` 를 **위에서부터 하나씩**: `update_tune(changes=<그 처방의 action.args.changes>, reason="P1")` → `evaluate`.
   점수(`span_score`)가 떨어지면 `revert` 하고 다음 처방으로.
4. `prescriptions` 가 비었는데 `individual` 이 남으면 `inspect_spans` 로 그 블록을 본다. 보정값 하나로 설명되는 일괄 이동이 아니면 손대지 않는다.
5. `engine_issues` 는 **네가 고칠 수 없다** (생성기 · 편집기 · 글꼴 파일 문제). 보정값으로 덮으려 하지 말고 `finish` 의 `summary` 에 그대로 적는다.

## 4. 관찰 읽는 법 (`evaluate` 결과)

| 필드 | 뜻 |
| :--- | :--- |
| `span_score` | 허용 오차(1px) 안 글자 비율 %. 목표 `target_score` |
| `prescriptions[]` | `{id, lesson(L-xx), rule, evidence, action}` — 코드가 계산한 처방. `action` 이 있으면 그대로 실행 |
| `engine_issues[]` | 보정값으로 못 고치는 원인과 고칠 곳 (`fix`) |
| `by_block[]` | 실패가 있는 블록 · 칸마다 `{block, spans, fail, missing, dx_med, dy_med}` |
| `individual[]` | 가장 많이 틀린 글자 8개 `{span, where(줄@블록), dx, dx1, dy}` |
| `notes[]` | 고칠 대상이 아닌 것 (기호 글꼴, 선 두께 정수 px 등) |
| `history[]` | 반복마다 점수와 바꾼 것 |

**부호**: `dx` · `dy` = 그려진 위치 − 원본 위치 (양수 = 오른쪽 · 아래로 밀림).
보정값은 `*_dx` · `*_dy` 양수 = 오른쪽 · 아래로 민다, `size_offsets` 양수 = 그 크기 글자를 **위로** 올린다.
처방의 `action` 은 이 부호를 이미 계산해 둔 값이다. 03 의 원시 `offset_suggestions_px` 는 부호 규약이 달라서 쓰지 않는다.

## 5. 하지 않는 것

* 처방 없이 보정값을 짐작으로 바꾸기. 한 번에 여러 원인 바꾸기.
* 같은 인자로 같은 도구 다시 부르기. 실행하지 않은 결과를 thought 에 사실처럼 쓰기.
* 허용 오차 · 목표 점수 바꾸기 (못 바꾼다).
* 표 칸 위치 · 합친 칸을 바꾸려 하기 — PDF 선에서 정해진다. 틀려 보이면 `engine_issues` 로 보고.

## 6. 한 턴 예

```json
{"thought": "P1 은 11.04pt 글자 24개가 dy +1.6 으로 같은 방향이라 L-05 크기별 오프셋 처방이다. 그대로 넣는다.",
 "action": "update_tune",
 "args": {"changes": {"size_offsets": {"11.04": 1.6}}, "reason": "P1 (L-05)"}}
```
