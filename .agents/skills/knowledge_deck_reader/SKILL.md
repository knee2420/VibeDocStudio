# 지식 덱 탐색 절차 (knowledge_deck_reader)

첨부(<context kind="deck">)에는 덱의 섹션 지도가 이미 들어 있다. 그 지도에서 출발한다.

## 1. 요청을 분해한다 (먼저 생각, 도구는 그다음)
- 유형을 정한다: 사실 확인 / 구조(몇 개 · 순서 · 어느 장) / 표 · 그림 값 / 비교 · 분석 / 작성 / 아웃라인.
- 분석 · 작성 · 아웃라인은 하위 질문 3~6개로 나누고, 각 하위 질문이 어느 섹션에 걸리는지 지도에서 먼저 짚는다.

## 2. 위치를 찾는다 (한 응답에 여러 도구를 함께 부른다)
- 구조 질문 · 아웃라인 → `knowledge.toc` (원문 순서 그대로의 목차, 개수 세기는 여기서).
- 뜻으로 찾기 · 말이 모호할 때 → `knowledge.lookup` (별칭 · 예상 질문 · 표 행 이름까지 본다).
- 정확한 용어 · 옵션 · 숫자 → `knowledge.grep`. 결과는 카드별로 묶여 온다: **줄을 다 읽지 말고**
  hits 가 몰린 카드와 제목이 맞는 카드만 고른다. 히트가 지도에서 예상한 섹션 밖에 있으면
  `knowledge.section` 으로 그 섹션을 확인해 범위를 다시 잡는다 (grep → 색인 확인 → 추림).
- 표 · 그림 · 예시 코드 → `knowledge.assets` (캡션 · 열 · 행 이름으로 바로 찾는다).

## 3. 읽는다
- 고른 카드는 `knowledge.cards` 로 한 번에 최대 6장. 요약 · 요소 표 · 자산 · 밖으로(연결)를 본다.
- 인용할 정확한 값 · 문구 · 표 셀은 `knowledge.source` 로 원문 줄을 확인한 뒤에 쓴다.
- `linksOut` · 관련 섹션(가로축)이 질문의 다른 면을 다루면 따라간다 (분석 · 작성에서 특히).

## 4. 범위를 점검한다 (분석 · 작성 · 아웃라인)
- 1에서 짚은 섹션을 모두 확인했는가? 빠진 섹션이 있으면 그 섹션 인덱스를 한 번 더 본다.
- 덱에 없는 내용은 "덱에서 찾지 못했다"고 쓴다. 추측으로 채우지 않는다.

## 5. 답한다
- 모든 핵심 주장 끝에 출처를 단다: `[C-SS-NN 제목](vdoc:kcard/<deckId>:C-SS-NN)` + 필요하면 원문 줄 `(원문 L120-L134)`.
- 작성 · 분석은 출처를 촘촘히 — 문단마다 최소 1개, 수치 · 조건 · 예외는 반드시 출처와 함께.
- 아웃라인은 원문 목차(toc)의 구조를 근거로 장 · 절을 세우고, 각 항목 옆에 근거 카드 id 를 적는다.
- 도구 호출은 보통 2~5라운드면 충분하다. 같은 도구를 같은 인자로 반복하지 않는다.
